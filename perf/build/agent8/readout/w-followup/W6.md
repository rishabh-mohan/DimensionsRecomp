## Round 1 and warm-up bias

- **Round 1 favours s0 in both passes.** In pass 1, s0, p2 and p2f all ran fast (2.05-2.20 ms against ~2.45 ms later), while p2fc ran at its usual speed (2.135 vs ~2.15). In pass 2, only the first run, s0's, was fast (2.270 ms, +8.6 % fps). So p2fc's paired gain is smallest in round 1 (+0.056 and −0.162 ms, against −0.27 to −0.35 elsewhere).
- Agent 7's round terms show the same thing: rounds 2-10 run 8.6-14.2 % slower than round 1.
- **Cause: GPU warm-up (audit §5.5).** After the idle gap before each pass, the GPU ran above its steady clock in the first runs: window means of 1257, 1134 and 1013 MHz for s0, p2 and p2f in pass 1's round 1 (and 909 MHz for p2 in round 2), and 1069 and 884 MHz for s0 and p2 in pass 2's round 1. Almost every other run sat at 832 MHz, the GPU's thermal limit: every GPU sample carries the software thermal-throttle bit, at 86-89 °C. Run fps follows the GPU clock (Spearman rho 0.53 in pass 1 and 0.52 in pass 2, p ≤ 0.017).
- In pass 1, p2fc ran 4th in round 1, when the GPU was already at 832 MHz, so it got no round-1 boost. The earlier lead (the fast state removes the cost C1 removes) is withdrawn.
- **Lead: at steady state this host looks GPU-limited.** After round 1, s0, p2 and p2f ran at 97-100 % GPU utilisation. p2fc ran at 86-89 % (82 % in the host-loaded 0023) while giving 18 % more fps. That is roughly 27 % less GPU-busy time per frame (utilisation ÷ fps, from a coarse NVML counter). So p2fc probably also cuts GPU-side work, and a change that only saves CPU would show up as fewer cores rather than more fps.
- Every window tonight shows a fast first scored run; see [W4c.md](W4c.md#round-1-and-warm-up-bias) for the table.
- **Suggestion for future windows:** warm the GPU before scoring, since tonight its clock settled only after 5-13 min of game load. For example, add discarded runs until gpu.csv shows the steady clock. Also rotate the first arm across rounds.

## Caveats

- **Cross-window:** W4b and W5 (`build/agent8/matrix/20261122-1541`, `20261122-1756`) ran on the **best_efficiency** overlay and **before** the Defender exclusion for `build/` was added (~23:16 Nov 22). W6 ran on best_performance, after the exclusion. Compare W6's arms within W6 only; absolute ms, fps and CPU don't carry over to W4b, W5 or older windows.
- **Verify off:** W6 timed keep-watch with `physical_protect_keep_watch_verify=false`. Verify on was exercised only in Agent 3's functional gate-A run, not timed. A verify-on build might give back part of the gain.
- **No C1-only arm:** the gain is measured on top of p2 and p2f. Both are null, so within this stack the gain belongs to C1. C1 alone is untested.
- **The episode's cause is unknown.** No recorded host or game counter shows it (audit §5.1), and the matrix has no per-process or disk data. It hit every arm, and the medians stayed in line.
- **Light share:** Agent 7's mix guard warns in every cut, because p2fc moves the mix toward light frames. T-light carries the gain.
- **Multiple tests:** with 12 tests, about 0.6 stars are expected by chance. The p99 star is consistent, though: +1.6 / +1.9 % per pass and +1.4 to +1.7 % in every cut.
