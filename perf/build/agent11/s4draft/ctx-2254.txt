L285: ### 10. The stuck game lock is a long wait, not a deadlock (Agent 6, 06:23; v0.2.0 confirmed 07:15)
L286: - **What happened:** 3 runs tonight logged a watchdog report that a game lock had been held for 5+ s, 6 reports in total: native3d on the long menu route, and devoffB and devoff3 (with a pre-filled shader store) on the attract sequence. All recovered, and every run closed normally with exit code 0.
L287: - **The pattern:** the render thread holds the graphics lock while it waits for the GPU, and the main thread, tearing down a scene, waits for that lock. On the native path the render thread was waiting for the driver to build pipelines (one frame built 56 in 4.3 s on a cold driver cache). On the standard path it was in the game's own wait loop for the GPU command thread, which never yields the CPU. In v0.2.0's run (07:15) the holder was in a different loop: it polled a GPU query result back to back with no pause, while the GPU command thread was compiling a shader. So shader and pipeline builds on the GPU command thread can feed these waits on the standard path too.
L288: - **A busy CPU makes it worse but doesn't cause it.** During those waits the CPU was 97-100% busy (Defender 1.2-4.8 cores, PresentMon 1), the game got only 1.3-1.8 cores, and the GPU was just 17-29% busy. All 3 runs fell between 05:03 and 05:32, the busiest stretch of the night.
L289: - **The watchdog adds to it:** its crash dump freezes the game for another 1.7-3.6 s at each first report.
L290: - **Not caused by our changes:** v0.2.0 does it too. Its first attract run (06:44) logged the same report with the same lock, owner and waiting thread, on the same busy machine (98% CPU), then recovered and closed normally (Agent 3). **Agent 6 confirmed it from the crash dump (07:15):** the same lock, the same owner object and thread, and a waiting chain identical to devoffB's, 219 s in. The 5 s hold plus the 3.5 s dump made one 8.6 s frame. Earlier evidence pointed the same way: devoffB predates the 05:02 fix, and native3d ran clean in the reverse-order check with a warm driver cache (187 pipelines in 283 ms).
L291: - **For S4 (proposals, off by default):** the fix for the standard path's busy-waiting wait loop (see "Leads"), which now covers this too as one item, with a stuck-lock check on a loaded machine in its test plan; the same kind of back-off for the GPU-query poll seen in v0.2.0's run, which the wait-loop fix alone wouldn't cover (Agent 6, 07:15); and pre-building the cached native pipelines at boot. Delaying the watchdog's dump until a lock has been held ~30 s is staged on scratch (diagnostics only), but it isn't an S4 item.
