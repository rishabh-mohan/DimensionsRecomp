# Re-pin after S4b: native3d / nativeB to the S4b bins

1. S4b changes two native fingerprint inputs: C1 v2's `memory_watch.cpp` and #24's `rexlego/CMakeLists.txt`. So every native bin built from the S4b tree gets a new GPU fingerprint. The line's pin moves once, to a new bin in a new folder: native5 on the 3d line, nativeB5 on the B line. The s35 pack and its index are unchanged, so nothing has to be regenerated.
2. Steps: pre-check ~15 s, S4b apply ~10-15 min, CMake and full rebuild ~37-46 min, pin record ~1 min, Agent 3's checks ~15 min. That's ~65-80 min from GO to pin. The optional pack bin native5p adds ~30-35 min, and the B line adds ~35 min.
3. Order: don't make native4p wait for S4b. Build native4p right after W4b so the user can look, roll the tree back (~1 min), then do S4b, native5 and native5p. The pack is copied twice, with no new pack run, and the line is re-pinned once.

Agent 4, board run 2, task #20, 2026-11-22 14:40. Notes and dry runs only: nothing was built, copied or run against the game. The script is `build/agent4/repin/repin_check.ps1`. It does a dry run by default, and `-Go` refuses to run without `-W4bDone`.

**How the fingerprint is computed.**
- `rexlego/CMakeLists.txt` 582-765 lists 271 inputs. They include `CMakeLists.txt` itself and `memory_watch.cpp`. The SDK diffs, #24's new TU and #26 are not inputs.
- 766-781 writes `<build dir>/generate-native-gpu-fingerprint.cmake`. It takes the sha256 of each input, concatenates them, takes the sha256 of that and keeps the first 16 hex characters.
- `repin_check.ps1` recomputes it: `5e3ff55de10f4f64` (snap1-on) and `81d1c3a71be3c096` (snapB3-on), both exact, in 4-12 s.

**The mtime trap (finding).**
- The fingerprint is an add_custom_command whose DEPENDS are the inputs (782-790), so it re-runs only when an input is newer than its output.
- `Copy-Item` keeps the source's mtime. The staged `memory_watch.cpp` is from 11-22 07:48, older than snap1-on's `native-gpu-build.txt` (13:33). After a plain copy, native5 would still report native4's `5e3ff55d…`. The same applies to the index: a plain copy wouldn't be recompiled.
- `repin_check.ps1 -Go` sets LastWriteTime to now after each copy. Its [4] check FAILs when the recomputed fp differs from the built fp and no input is newer than the output.

**(b) Identity check and the new n-row baseline.** `powershell -NoProfile -ExecutionPolicy Bypass -File bench\agent8\run\run-matrix.ps1 -Matrix build\agent4\repin\matrix-repin-native5.json -NoPrompt`. 4 runs, ~15 min: n0old on native4, then n0, n2 and n3 on native5. Pass:

- `python bench\agent4\check_n_rows.py --baseline <n0> --rows n2=<n2> n3=<n3>` exits 0: threaded recording ON, `parallel workers=2` in n2, no hash=0 lines.
- n0, n2 and n3 become the new n-row baseline.

**(c) Pack hit.** Like run-071627's lookups, but in the game. `… run-matrix.ps1 -Matrix build\agent4\repin\matrix-repin-packhit.json -NoPrompt`. 2 traced runs, ~12 min: t0 on native5 and t0p on native5p, each with a 30 s warm-up and a 240 s window. Both arms get `LEGO_NATIVE_TRACE_DIR=<run>\trace`; the game creates that dir (`src/gpu_native/long_probe.h:49`). Pass:
- **t0 is the positive control.** It must have `draw_missing_vertex_shader` / `draw_missing_pixel_shader` rows and the placement "missing from AOT index" lines (native4 n0 has VS `0xAC449538` ×4 and PS `0xAC448F28` ×4). If t0 has none, the check is void, not passed.
- **t0p must have:**
  - 0 `draw_missing_*` rows;
  - no placement "missing from AOT index" lines, and no "unrecognized … resource" lines for the packed addresses;
  - draws per frame (p10/p50/p90) ≥ t0's;
  - `check_n_rows.py --baseline <t0> --rows t0p=<t0p>` exiting 0;
  - a clean exit.
- **On a fail,** follow VISUAL-CHECK §5: Agent 2 checks the prelinked cache, I re-run the offline lookups, native5p is parked and the pin stays native5.

For native4p before S4b (§4, step 2), it's the same matrix with t0 on native4-bin and t0p on Agent 2's native4p folder. That run is VISUAL-CHECK §3.1.

## 4. native4p vs S4b: my order

**Don't make native4p wait for S4b.**

1. W4b.
2. native4p on snap1 (S4a plus the pack; VISUAL-CHECK §2). Run `repin_check.ps1 -Line snap1 -Pack -Go -W4bDone`, then Agent 2's `cmake -D` and build: ~3 min + 10-15 min prep, ~364 MiB, in a new folder. Agent 3 runs the pack pair native4 vs native4p (~12 min). Then the user looks (VISUAL-CHECK §4, ~15 min).
3. Roll snap1 back to no-pack with the printed rollback (~1 min). This must finish before S4b touches snap1.
4. S4b apply, then native5 and devoff5. Re-pin once (§2 steps 0-5).
5. native5p from the same tree (§2 steps 6-8). No second look: the pack bytes are the same, and S4b's only native change is a latch store in `memory_watch.cpp`.

Why:
- The user can look in the same sitting, ~35-40 min after W4b. Waiting for S4b would push the look to ~1.5-2 h after W4b (S4b prep and build, then native5p and its checks).
- native4p is a test bin and is never pinned, so it costs no re-pin. The pack is produced once; the second copy costs ~1 min.
- S4b can't start before the user picks the line anyway. The look is valid on either line, because both use the same 4 DXIL entries.
- If the user picks the B line, native4p doesn't touch snapB3 at all.

**Pin rule.** Pin native5p if the user said yes and step 8 passed; otherwise pin native5.
- If the yes comes after native5 is pinned, moving to native5p is a second re-pin: step 3 plus the step 4-5 checks, ~20 min.
- If S4b's GO comes before the user's slot, skip native4p and show the user native5p vs devoff5 instead.
