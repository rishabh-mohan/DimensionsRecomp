### 6. The timer thread busy-waits (Agent 11, found 03:05, cause found 04:04)
- **The cause:** the game's only TimerQueue user is a 1 ms repeating timer that updates the guest's tick count. Each wait first spins for ~0.4 ms, even when the deadline has already passed. Then it sleeps for 1 ms, which takes ~15.4 ms at Windows' default timer resolution. The missed ticks then fire back to back, each with its own spin: about 1,000 busy phases per second.
- **The cost:** 31-44% of a core in tonight's hidden-desktop runs, and 62% in window 3 (foreground).
- **Fix without a rebuild (d11t, in window 4):** window 3's timer settings (1 ms timer resolution and the related cvars) plus the blocking timer wait (`REX_TIMER_WAIT_BLOCKING=1`). In 4 test runs the timer thread dropped to 0.3-0.5% of a core, and the game's total CPU fell from 2.2-2.4 to 1.8-2.1 cores. All of them closed cleanly, with no new log lines. Window 4 measures whether that turns into frame rate in the foreground.
- In a bench without the game, the blocking wait alone lets the tick count go more than 2 ms stale 84.5% of the time (it moves in 16 ms steps). That's why it only runs together with the 1 ms resolution: then 1.4% CPU and 4.7% stale, against 30.4% CPU and 49.7% stale for today's spin.
- **For S4:** Agent 11 staged a cleaner fix (`timer_queue_precise_wait`, OFF by default): 1.9% CPU and 5.4% stale in the bench. Agent 10 rated it safe as a default-off candidate, and it is in S4a, off by default. In W5b (Nov 23) it saved 0.20 core (−8%) with no consistent cost in frame rate or the slowest frames; Agent 7's read-out picks it, narrowly, over the blocking wait, which saves about the same but costs about 1% fps.

### 7. Agent runs on the hidden desktop can't be timed (the slow state)

### 8. The attract sequence's first-view freezes are shader compiles (Agent 6, 04:30)
- The 1-5 s freezes when the attract sequence first shows a scene happen because its GPU pipelines are built on first use. The draw is skipped, but the GPU thread then waits for every queued pipeline at the next frame swap. This explains 96% of the frames over 250 ms in the devoff2 run and 72% in the B run.
- Update 05:50 (Agent 3): in one run with the shader store pre-filled from an earlier run, first-use pipeline builds dropped from 264 to 56, and none fell in the proposed benchmark window. That run, on a busy machine, still had 2-10 s frames with no pipeline builds; those came from CPU starvation.
- The emulator's shader cache is on by default, but it is cold in every test run, because each run gets a fresh user folder. Players keep it from their second launch on, so they would see most of these freezes only the first time (a few slow frames remain either way).
- The NVIDIA driver's own cache is shared across runs and already warm. Warming it halved the cost per pipeline (116 → 58 ms).
- No code change is needed for a benchmark: copying two cache files into a run's folder before launch should remove most of these freezes (untested), for an estimated 1-3 s of extra boot.
- Window 3 and window 4 measure the title screen from at least 60 s after the first frame, and window 3 showed no such freezes (p99 12 ms), so their results aren't affected.

### 10. The stuck game lock is a long wait, not a deadlock (Agent 6, 06:23; v0.2.0 confirmed 07:15)
- **What happened:** 3 runs tonight logged a watchdog report that a game lock had been held for 5+ s, 6 reports in total: native3d on the long menu route, and devoffB and devoff3 (with a pre-filled shader store) on the attract sequence. All recovered, and every run closed normally with exit code 0.
- **The pattern:** the render thread holds the graphics lock while it waits for the GPU, and the main thread, tearing down a scene, waits for that lock. On the native path the render thread was waiting for the driver to build pipelines (one frame built 56 in 4.3 s on a cold driver cache). On the standard path it was in the game's own wait loop for the GPU command thread, which never yields the CPU. In v0.2.0's run (07:15) the holder was in a different loop: it polled a GPU query result back to back with no pause, while the GPU command thread was compiling a shader. So shader and pipeline builds on the GPU command thread can feed these waits on the standard path too.
- **A busy CPU makes it worse but doesn't cause it.** During those waits the CPU was 97-100% busy (Defender 1.2-4.8 cores, PresentMon 1), the game got only 1.3-1.8 cores, and the GPU was just 17-29% busy. All 3 runs fell between 05:03 and 05:32, the busiest stretch of the night.
- **The watchdog adds to it:** its crash dump freezes the game for another 1.7-3.6 s at each first report.
- **Not caused by our changes:** v0.2.0 does it too. Its first attract run (06:44) logged the same report with the same lock, owner and waiting thread, on the same busy machine (98% CPU), then recovered and closed normally (Agent 3). **Agent 6 confirmed it from the crash dump (07:15):** the same lock, the same owner object and thread, and a waiting chain identical to devoffB's, 219 s in. The 5 s hold plus the 3.5 s dump made one 8.6 s frame. Earlier evidence pointed the same way: devoffB predates the 05:02 fix, and native3d ran clean in the reverse-order check with a warm driver cache (187 pipelines in 283 ms).
- **For S4 (proposals, off by default):** the fix for the standard path's busy-waiting wait loop (see "Leads"), which now covers this too as one item, with a stuck-lock check on a loaded machine in its test plan; the same kind of back-off for the GPU-query poll seen in v0.2.0's run, which the wait-loop fix alone wouldn't cover (Agent 6, 07:15); and pre-building the cached native pipelines at boot. Delaying the watchdog's dump until a lock has been held ~30 s is staged on scratch (diagnostics only), but it isn't an S4 item.
- **Tonight's runs and the likely mechanism (Agent 6, 22:52; `build/agent6/hang/cp-state-s4b24-s4b20.md`, gate A: `cp-state-gateA.md`):** 4 of 13 functional runs hit it (w6gA, s4b24, s4b20, w6gB). All recovered, and all ran while an 8-job build kept the PC at 100 % (SESSION2 L2990, L3081). From the gate A, s4b24 and s4b20 crash dumps (function names inferred; the GPU backend has no symbols): the render thread holds the graphics lock while it polls a GPU fence, and the main thread waits for that lock. Meanwhile the GPU command thread is in a draw that reads memexport data back, and on that path it ends the submission and waits, with no timeout, until the GPU has finished every draw before it. So the 5 s report fires whenever the GPU command thread is slow: verify mode in gate A, a starved PC in all three, or very many of these syncs (L3114-3119). It needs neither verify nor C1: s4b20 had both off (L3010-3012). It hasn't been seen on a quiet PC. Tonight's timing windows run the title and attract screens only, so they don't test it; the direct test is two untimed level runs on the quiet PC after the last window, one with C1 off and one with it on (L3108, L3112-3123).
- **Possible speedup after S4 (Agent 6):** the readback's fast path skips the wait only when the other slot's submission has already finished, so same-key draws inside one submission alternate between the fast and the full path. When the GPU runs behind, nearly every such draw takes the full path: a submit, a round trip, a wake-up and a second copy. Gate A's 9.7 s frame logged 1244 of these syncs, against 5-62 normally (L2927). It isn't measured at normal speed yet; the quiet-PC level runs will give the counts (L3120, L3124).
- **The quiet-PC test (Nov 23, Agent 3, `build/agent3/f10/RESULTS.md`): no hang.** With the same sync bursts, each host-to-GPU round trip took 0.2-1.0 ms on the quiet PC against 1.8-6.1 ms in a run that hung under the build, so the busy host, not the GPU, stretched the stalls. P2 + fix (i) + C1's biggest bursts (2736 syncs in one frame) still took up to 2.9 s, so a busier or slower PC could push one past the 5 s detector; the set with C1 off made none of those bursts in either of its runs (its biggest, 1644 syncs in one frame, took 1.5 s). A second pair didn't hang either: 0 of 4 quiet runs against 4 of 6 under the build (p = 0.07), which fits load as the trigger without proving it. Agent 10 rates all four runs PASS, and finding 10 stays a load-only warning ([rating](<workspace>/build/agent10/t27/f10-rating.md)). A third quiet pair, a controlled-load repeat and a loaded s4b20-style row are offered, not run.

### 11. Gaps in the emulator's write tracking (Agent 12 found, Agent 10 confirmed, 06:40)
- **What it is:** the emulator keeps a GPU-side copy of guest memory and watches those pages for writes, so it knows when to upload them again. When the game changes a page's memory protection, that watch can be lost while the GPU copy stays marked as current. Later guest writes then go unseen, and the GPU can draw from stale data. Both reviews are code reading (`PhysicalHeap::Protect` in `xmemory.cpp`). Nothing visible has been traced to it tonight.
- **Form 1, a race (writable → writable, like the game's per-frame buffer lock):** the emulator releases its global lock between running the watch callbacks and changing the host protection. A GPU upload in that gap can re-arm the watch, and the protection change then makes the page writable while it's still marked as watched. Writes are missed until the next lock of that page, about one frame later for the vertex buffer.
- **Form 2, no race needed (read-only → writable):** read-only pages are never watched, so making one writable doesn't invalidate the GPU copy. This gap is in the upstream code as it stands. Agent 10 found no trigger for it in this game, which only ever sets read-write protections (06:52).
- **Fixes for S4** (they change behaviour, so each gets its own rating and switch): (i) keep the global lock across both host protection changes, which closes form 1 (it takes the locks in the allowed order); and, for form 2, invalidate on any protection change that adds write access.
- **Link to the re-upload fix (C1):** today the game's next lock repairs form 1. C1 keeps the watch through those locks, which would remove that repair, so C1 lands only together with fix (i). Agent 10's note on the remaining risk follows.
